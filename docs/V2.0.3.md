# v2.0.3: Scoped Skills and HTML delivery

The design workflow remains Orchestrator → Designer → Reviewer → Builder,
with Researcher supplying evidence through the existing routing and revision
loop. Orchestrator identifies categories; Designer owns knowledge selection and
design; Reviewer approves the specification; Builder executes approved outputs.
Pi remains the upstream runtime and resource loader.

## Category and task assignment

Orchestrator passes `designScopes` to `run_init`, or explicitly updates them in
`run_revision`. The runtime persists them in `brief.json::resolvedScope.designScopes`.
Each scope has a unique stable `id`, category, concrete task and optional rationale.
Multiple scopes can use the same category. Do not add categories merely because
an object could need that work.

```json
[
  {"id":"hardware","category":"industrial","task":"Design the connected lamp"},
  {"id":"controls","category":"ux","task":"Design its control interface"},
  {"id":"campaign","category":"media_communication","task":"Design the launch poster"}
]
```

The category registry also retains space, fashion, game and service extensions.
It is not a keyword classifier or a separate classification Agent: the existing
Orchestrator reasons about user requirements and supplies validated assignments.

## Existing knowledge mapping

Skill frontmatter describes applicability, not a compulsory selection or tool
permission. The 21 existing Skills remain discoverable through Pi. Metadata adds
`design_categories`, `module_type` and `supported_outputs`; Designer chooses by
task and professional responsibility, including useful cross-category support.

| Category | Professional Skills |
| --- | --- |
| media_communication | brand-identity, poster-advertising, editorial-design, illustration-art-direction, information-design, media-motion-design, packaging-design, exhibition-wayfinding |
| industrial | industrial-design, product-design, packaging-design |
| ux | ux-design, ui-web-design, digital-product-design; information-design, service-design, game-experience-design and illustration-art-direction where relevant |
| space | architecture-space, exhibition-wayfinding |
| fashion | fashion-textile-design |
| game | game-experience-design |
| service | service-design |

`design-system` and `visual-composition` supply cross-domain knowledge;
`image-prompting` supplies image expression; `showcase-layout` guides Builder's
Gallery presentation. New `html-interface` supplies UX page expression and
delivery contracts alongside professional UX/UI knowledge. Existing motion/game
knowledge does not enable video, game-engine or 3D execution.

Designer calls `list_skills({scopeId})`, then
`use_skill({name, scopeId, role: "primary" | "supporting"})`.
Each scope has an independent primary. Replacing it does not replace another
scope's primary; `deactivate` removes obsolete supporting bindings in that scope.
Unfiltered discovery allows other-category support. `refresh: true` refreshes the
catalog, and `reload: true` reloads a needed body after compaction. New specialist
invocations must load their required knowledge again.

Catalog descriptors are cached within an invocation; discovery does not load
whole bodies into the model. Repeated unchanged loads return reuse information.
The runtime records names, scope, role, version, metadata and source hash in
`.performance/skills-designer.json`; unchanged records are not rewritten.
Designer records matching `{scope_id, name, role, rationale}` entries in
`design_plan.json::skill_selection` and links deliverables through `skill_refs`.
Completion rejects claims about unloaded modules or assignments to the wrong
category. If discovery confirms there is no professional module for a scope,
`skill_gaps: [{scope_id, reason}]` documents the gap; unavailable knowledge must
not be claimed as loaded. This exception cannot bypass available modules.

## Output contracts and execution

Historical unclassified image plans keep their v1 contract and
`image_generation_plan`. New classified image-only plans can also use that
contract, adding scope/category/Skill associations. Their prompts, image sizes,
edit semantics, provider adapter, retries, queue and Gallery finalization retain
the existing execution path.

HTML or mixed plans use `schemaVersion: 2` in both design plan and manifest, with
root `execution_plan`. Every task matches its deliverable id, category, scope and
method. Supported automatic methods are image_generate, image_edit and
html_generate; manual deliverables keep their existing explicit implementation
contract. Dependencies are validated and executed before dependent tasks.

Designer authors complete page content, layout, styles and local interactions
under `plan/html/<scope-id>/`. The `html-interface` Skill includes a complete task
example: `files` source/output mappings, `resources`, `dependencies`, viewports
and declarative interaction checks. HTML deliverables use `kind: "html_page"`
and declare their actual entry file under artifacts/. They need no image prompt
or size. Classified UX scopes must include HTML output; screenshots alone cannot
silently replace the requested page.

Builder calls `execute_design_plan` for the required set or selected approved ids.
The executor registry groups ready tasks by mechanical method; images delegate
to the existing `execute_image_plan`, and HTML delegates to the new source-based
page generator. `html_generate(runId, id)` executes a single approved page task.
It copies approved source bytes, without another model call or redesign.
Completed matching outputs are reused; dependency failures preserve independent
successes. Optional outputs are not forced unless selected or needed as a
dependency/presentation entry.

Source mappings are confined to the Run and checked against physical paths.
Local resources come from research/assets/ or declared artifact producers.
Generated resources require a dependency on their producing task. Shared
resources and relative page links can cross subdirectories within the declared
artifact set. Duplicate output ownership and dependency cycles are rejected.

## Review, presentation and export

Designer commits the specification, source files and Skill activation evidence.
Reviewer checks category coverage, actual Skill associations, existing image
prompt requirements and proposed page content/layout/states/interactions.
Its approval receipt includes Designer inputs. Execution and finalization reject
changed approved inputs and stale approval gates; user revisions open the
existing new workflow cycle rather than reuse old approval.

The manifest declares a presentation:

- `{"mode":"html","entry":"artifacts/controls/index.html"}` uses the actual
  page as Showcase. It needs no generated UI image or extra Gallery. Research
  remains in the package, without an appendix inserted into the interface.
- `{"mode":"gallery","entry":"artifacts/00-gallery.html"}` retains the image
  Showcase and reference appendix. Mixed Gallery presentation links approved
  pages in new tabs; `showcase_template` can render these links alongside images.

`presentation.entry` is one Run-relative HTML homepage used by execution,
finalization, Showcase/preview and export; it is not an output collection.
Before a Designer manifest save is serialized and hashed, the runtime fills
only deterministic omitted fields: Gallery has the fixed entry above; HTML
uses the sole `html_page` deliverable's declared `file`. A task may have many
pages while its deliverable names the main page. Pure image or pure HTML
manifests can also supply an omitted mode. Mixed/manual manifests require an
explicit mode; multiple HTML deliverables require an explicit entry. The
runtime never chooses from `artifacts[]`, selects the first task file, rewrites
an explicit path, or drops required images to make the choice unambiguous.

`write_json`, `patch_json` and native Designer manifest writes share this policy.
Structured saves return `normalizedFields` and the SHA of the actual completed
bytes; ambiguous structured drafts are saved with immediate warnings, while
native writes require the explicit choice. Completion runs before any approval
receipt. Read, publish and execution paths remain strict and read-only; historical
or changed approved manifests are not silently repaired or rehashed.

`build_finalize` checks required files, approved-source equality and local
references. Gallery retains static resource/script rules; approved prototypes
allow local JavaScript. If a Chromium browser is available, it also checks
declared pages at their viewports, resource/script errors, horizontal overflow
and declared click/fill/press/assertion sequences. It records exactly the evidence
obtained; unavailable browser validation is not reported as an interaction pass.
This is mechanical validation, not proof of aesthetics, engineering feasibility,
backend integration or user acceptance.

| Environment | Behavior |
| --- | --- |
| DREAMATIC_HTML_BROWSER_EXECUTABLE | Optional installed Chromium executable path; otherwise discover a local browser |
| DREAMATIC_HTML_BROWSER=off | Static validation only |
| DREAMATIC_HTML_REQUIRE_BROWSER=true | Fail HTML finalization if browser validation is unavailable |

No browser is downloaded automatically. Playwright is loaded only for HTML
browser validation. Existing image execution does not launch a browser.

Server's lazy PreviewService uses a separate localhost origin with no application
API, opaque grants, restrictive CSP and committed-file hashes. Preview rejects
uncommitted/tampered files and is revoked on revision. React uses a scripts-only
sandbox for prototypes, with page and viewport selectors; the existing static
Gallery iframe keeps its previous sandbox. Plan sources and staging files do not
appear as built assets. Export preserves HTML's actual entry/resources, or the
existing Gallery entry/base adaptation.

## Extension and compatibility boundaries

New knowledge normally requires a Skill and applicability metadata. A new
category also requires a category-registry entry. A new output capability requires
an explicit contract, executor registration, review/receipt rules and delivery
support; Skill metadata never grants tools on its own. Video and 3D remain future
adapters rather than fallback behavior.

Agent Markdown changes are limited to category ownership, scoped loading and
conditional output contracts. Researcher is unchanged. The 18 existing non-UX
Skill bodies are unchanged; their frontmatter only gains mappings. Three UX
Skill bodies gain local page-expression guidance. Image copy, coverage,
preservation, one-pass generation and quality reasoning instructions remain.

Regression coverage includes scoped switching/discovery/reload, legacy tool
contracts, exact image prompt forwarding, image/page dependencies and reuse,
approval/source tampering, optional HTML, mixed Gallery/export, physical path
escapes, isolated preview and real-browser interaction checks. Live provider
quality and model latency still need comparison with fixed briefs/providers;
local regression tests do not establish unchanged creative quality.

## Action failure corrections

See [ACTION_FAILURE_ANALYSIS.md](ACTION_FAILURE_ANALYSIS.md) for observed failures,
root causes and replay evidence. Shared outputs may declare contributing_scopes
with scope_id, category, skill_refs and purpose. Responsive interaction checks
may declare viewport width bounds; assertions may select any/all/unique matching.
Deterministic design validation failures return a repairOwner and block repeated
Builder launches against the same approval and runtime. New approval or corrected
runtime allows recovery. DREAMATIC_TOOL_PATH optionally exposes installed tools
through Pi's normal tool resolution.

## Scope/Skill runtime handoff

`scopeId` is a task identifier from Orchestrator's persisted designScopes;
`category` is a registry domain (`ux`, `industrial`, `media_communication`, etc.);
`name` is a discovered Skill name such as `ui-web-design`. They are separate
namespaces. run_init returns the assignment and scopeProtocol. The runtime adds
that same protocol to specialist system context, and design_context_read returns
it for Designer, Reviewer and Builder. Skill metadata maps knowledge to domains;
Orchestrator does not select Skills on Designer's behalf.

New Run initialization requires nonempty designScopes (at the argument root or
inside resolvedScope); missing classification fails before creating Run outputs.
Existing unclassified historical Runs may resume with their original contract.

list_skills returns applicableScopes and concrete per-scope use_skill arguments.
If a Skill name or category is mistakenly supplied as scopeId, discovery may
resolve a unique matching assigned task and reports the canonical id explicitly.
When multiple tasks match, it returns all assignments and recovery guidance
without choosing or activating one. use_skill requires an exact assigned scope
id and returns structured recovery information for an unknown id without changing
the activation state. The legitimate assigned id `project` remains supported.

Designer commits must persist the current invocation's actual activation state;
an earlier invocation's receipt cannot substitute for loading required knowledge.
The approved specification binds scope_id/category/skill_refs to deliverables
and execution tasks. Reviewer gates and hashed receipts protect that linkage.
Builder executes approved methods through the executor registry: image tools for
image methods and html_generate for page methods. Classified UX work requires
an HTML page; unclassified historical workflows retain their existing contract.


## Workflow publication recovery

Specialist publication attaches canonical stage files only after validating the
actual outputs; artifactRefs is optional for extra existing assigned-Run files.
Missing or empty required outputs, invalid extra references, ownership violations
and physical path escapes still prevent publication. Receipts hash the real files.
Designer initial/revision events explicitly route to Reviewer with nextAgent and
requestedAction=review; a submitted proceed_to_build is retained as provenance,
not authorization to skip approval. Builder's existing approval gate remains.

HTML resources are local source/output mappings. Google Fonts external_url/url
objects do not satisfy this contract; errors name the plan, task and array index
and explain local font/system-font alternatives. Neither a URL declaration nor
a license bypasses the local prototype contract. The product action label is
“Publishing workflow result”; successful publication requires the committed event.


### Showcase entry selection

The Canvas retains a single Showcase button. For a completed typed delivery
whose presentation mode is HTML, clicking it requests the declared HTML entry
from the isolated preview service and displays the designed page with its
CSS/JS and interaction controls. Gallery presentations and legacy image Runs
continue opening their Gallery file. HTML preview failures have an explicit
retry action; pending builds remain unavailable and in-flight requests cannot
replace a different project's preview. Switching projects or rebuilding clears
preview state. No extra Gallery is generated for an HTML presentation.

Browser regression: `node --test apps/web/test/showcase.test.mjs` verifies the
actual React Canvas click, CSS and language interaction, retry, pending-build
gate, and Gallery routing. Existing server tests cover committed-file isolation.


### Declared image path and encoding

Image output formats come from one runtime contract: PNG (default, lossless,
transparency) and JPEG (`.jpg`/`.jpeg`, lossy, opaque). A base64 JSON or URL
response is a transport choice, not an image encoding. The output writer keeps
the manifest's exact filename and converts provider PNG/JPEG bytes locally when
necessary; it never just changes the suffix. Same-format bytes remain unchanged,
and conversions preserve dimensions. JPEG conversion uses quality 95.

Designer declares `deliverables[].file` once. Classified/typed Builder image
tools verify the current Designer/Reviewer receipts and bind that path by id;
`outputPath` can be omitted. A conflicting explicit path, unknown planned id or
changed approval is rejected before provider work. Standalone legacy tools keep
their existing PNG default. Saving, publication, execution and encoding share
the same format capabilities; typed finalization also verifies that actual image
bytes match the declared extension. JPEG outputs retain correct MIME metadata,
source dependencies, local HTML resource paths, Gallery links and export names.

### Preview actions and project download

The product tab is now **Preview**. HTML and Gallery presentations both expose
**Open** (the same existing new-window preview URL) and **Export**. HTML previews
fit the available width without a viewport selector; multi-page deliveries keep
their page selector. HTML still runs on the existing isolated preview origin.

`GET /api/runs/:runId/export` creates a disposable ZIP snapshot of the completed
Run's artifacts, plan (including HTML sources), research, review, local references,
brief and run state. Relative paths and approved output bytes remain intact. The
archive includes a portable `index.html` launcher and `package-manifest.json`.
It uses the server's `zip` utility, streams the download, and deletes temporary
files after completion or disconnect. It does not invoke an agent, update workflow
state, or require an earlier agent `export_package` call. Pending builds and changed
or missing committed outputs cannot be exported. Sessions, caches and historical
Runs are excluded. The browser reports export failures and permits retry.
