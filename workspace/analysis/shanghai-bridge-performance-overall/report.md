# Dreamatic 上海长江大桥案例：全部性能变化与瓶颈

截至 2026-10-12（Asia/Shanghai），15 个已找到的案例、801 次文本请求、758 次专业角色工具结束事件、89 次图像接口尝试。本报告基于本地原始运行日志，保留各轮不同交付规模与代码版本的限制。

**结论：近期文本消耗更低、无效往返在部分案例中减少；但墙钟耗时没有稳定下降。常规瓶颈在 Designer 与逐渐增长的 Reviewer 文本响应，最严重尾部风险来自图像接口。工具契约和页面验收缺陷是可重复定位的修复成本。**

## 总体水平

- 15/15 案例状态 complete；这只是当前已找到的案例，不是全系统成功率。
- 总历时平均 25.94 分钟、中位数 23.64 分钟，范围 19.81–51.31 分钟；流程历时平均 24.09、中位数 22.75，范围 17.83–50.27 分钟。总历时包含前期澄清/等待，流程从 design_categories_identified 起算。
- 累计总历时约 389.12 分钟（各项目相加，不代表同一连续服务时段）；累计文本 Token 30,400,729，平均 2,026,715/项目。
- Token 构成为 8,289,222 未缓存输入、21,294,208 缓存读取、817,299 输出；cacheWrite=0。输入侧缓存占比约 72.0%，输出仅占总量 2.69%。reasoning 179,328 已包含在 output，不重复叠加。
- 80 张生成图对应 89 次接口尝试，9 次重试；7 次重试因响应 body 停滞，2 次因接口 503。接口失败尝试约占 10.1%，最终图片均完成；不能把尝试失败率当作项目失败率。

## 瓶颈一：文本阶段，Designer 最大，Reviewer 不稳定

| 角色 | 累计 Token | Token 占比 | 平均专业阶段 min |
|---|---:|---:|---:|
| designer | 14,816,825 | 48.7% | 9.10 |
| researcher | 5,333,732 | 17.5% | 4.00 |
| reviewer | 5,312,379 | 17.5% | 2.52 |
| orchestrator | 3,891,718 | 12.8% | 无独立专业阶段 |
| builder | 1,046,075 | 3.4% | 6.25 |

- Designer 占文本 Token 的 48.7%，平均阶段 9.10 分钟；累计阶段时间 136.50 分钟，其中模型响应约 132.73 分钟。工具本身通常不是主要等待源，输入重复、生成轮数和长响应更值得关注。
- Reviewer Token 占比 17.5%，与 Researcher 相近；平均时间初期 2.03 分钟、中间 3.27 分钟、最近 4 次 2.93 分钟。最新 187992dd Reviewer 达 5.49 分钟，成为该次主要时间增量，不能只优化 Designer。
- 37287fbf Designer 请求 17→9（对比 8f5c190b），Token 105.2→50.2 万，同时输出增加；集中更新清单、选择性读取研究结论与减少往返具备直接日志证据。
- 905cf94e 有一次 279.7 秒推理响应，reasoning=output=16,384、stopReason=length，消耗 71,035 Token，随后 agent_retry。单次占该项目总历时约 23.5%。这是严重但只观察到一次的截断风险；不能以零复发证明已解决。

## 瓶颈二：图像接口是最严重长尾来源

- 最慢项目 cc1a21e4 总耗时 51.31 分钟，Builder 33.71 分钟（约 66%），5 图产生 8 次尝试和 3 次重试；其 Token 仅 180.7 万。总 Token 与总耗时不能互相替代。
- 单次最长图像尝试 976.8 秒，日志显示 body 长时间传输/停滞后重试；这个指标包括失败尝试，不等同于最终某张图纯生成时间。
- 37287fbf 无图像重试，却有一张成功图像响应 336.6 秒，决定 execute_design_plan 约 336.7 秒。只看失败次数会漏掉成功请求长尾。
- 905cf94e 5 张成功图像仅 18–42 秒，使 Builder 1.56 分钟；该次最好总历时部分源于交付减少与图像服务较快，不能视为内部吞吐稳定改善。
- 最新 187992dd 的两次 503 快速失败加退避约 3.94 秒，影响小；报文 CPU overloaded 是接口服务返回的信息，不是 Dreamatic 本机 CPU 使用率。
- 需要分别跟踪 headers、body、停滞、退避、失败尝试和成功请求尾部，并用并行任务关键路径而非调用耗时之和解释墙钟时间。

## 瓶颈三：可重复的契约错误和交付修复

758 次专业工具结束事件中 32 次标记错误（约 4.2%）：Designer 20、Reviewer 7、Researcher 4、Builder 1。按错误摘要分类：字段/参数契约 12、HTML 预检 8、路径/资源/角色权限 7、Skill 资格 2、事件权限 2、交付溢出 1。这些不是同一种严重性，次数不能直接代表时间成本。

- Reviewer 多次把 issues、resolved_issue_ids、remaining_risks 写在 changes 根字段；5c05dd55 连续四次失败，37287fbf 与最新 187992dd 又各出现一次。错误反馈已明确，但首次调用仍不稳定，是可重复问题。
- 页面预检问题包括移动导航未展开、选择器不唯一、目标元素不在视口；8 次预检失败证明验收步骤与实际页面行为的匹配仍需改进。
- 30797739 因 375px 横向溢出重新派发 Designer→Reviewer→Builder；从首次构建受阻至导出约 7.31 分钟、23 次响应、879,655 Token。该时段含重审、调度等，不是纯 CSS 修改成本，也不是严格反事实增量。
- 两次不兼容的 Skill primary 选择、路径打错及修改不允许的 artifacts 文件等问题造成额外往返。角色边界拒绝了错误写入并支持恢复，但恢复成本仍存在。

## 瓶颈四：研究、前期等待和串行流程

- Researcher 平均约 4.00 分钟，通常较稳定；37287fbf 抓取工具累计从约 39.6 增至 140.6 秒，研究阶段增加约 2.57 分钟，说明外部网页获取也有长尾。
- 50ba3b59 总耗时 31.67 分钟，真正设计流程 22.92 分钟；前期约 8.75 分钟不能算作模型计算慢。看板需区分前期澄清、流程执行、导出。
- 四个主要角色在这些记录中按研究→设计→评审→构建顺序运行，阶段未重叠；图像工具内部并行。串行前置阶段使各角色延迟累积，但有真实研究/审查依赖，不能简单承诺并行化即可解决。

## 可观测性变化与解释边界

- 初期日志写 configuredThinkingLevel=off，但 905cf94e 实际有大量推理并触发截断。最新日志更明确地记录 configuredThinkingLevel=null、sessionThinkingLevel=off、controlState=unspecified、reasoningCapability=unknown、offControlUnconfirmed=true；这改善了观测准确性，不证明模型推理真正关闭。
- Token 汇总需包含缓存读取并单列未缓存输入；真实费率与图片 Token 未记录，不能从 usage.cost=0 推断免费，也不能把总 Token 下降比例当作账单下降比例。
- originalRequest 在近期相同，但系统解析后的 resolvedScope 在 space、space+media_communication、industrial 之间变化，生成图数量 5–7 张；同一句用户请求不等同于系统承接同一负载。
- 多个代码指纹与 Skill 内容版本，部分早期项目一次运行中出现多个指纹；样本量小且非受控，不能用时间顺序推断代码变更因果效果。
- 最终 fileIntegrity/interactions 均 passed，但 visualFidelity 未评估、engineeringFeasibility 未验证、userAcceptance 待定。原始需求中的可编辑 3D 模型没有被最终图片/HTML清单证实，不能宣称所有需求均完成。

## 优化优先级与复测方法

| 优先级 | 行动 | 衡量指标 |
|---|---|---|
| P0 | 稳定 Reviewer 字段嵌套与验收步骤，阻止空提交/不必要补充 | 每角色修复率、修复响应数/Token、一次提交通过率 |
| P0 | 校验实际 thinking 控制与输出上限行为，避免长推理占满预算 | reasoning Token、offControlUnconfirmed、length 事件、失败尝试时间 |
| P1 | 按角色选择研究 sections、集中但不过大的设计更新 | 请求轮数、未缓存输入、缓存读取、正常生成与修复分开 |
| P1 | 监控图像成功和失败长尾，保留单项重试与已成功成果 | 成功请求尾部、body停滞、重试等待、并行关键路径 |
| P2 | 固定研究预算并记录抓取等待 | 单次/批次抓取时间、缓存复用、失败率 |
| P2 | 固定 brief、scope、图像数/尺寸、Skill和代码版本重复复测 | 同规模流程中位数/尾部、质量状态、文本消耗 |

建议保留两种不同基准：固定 7 图 + HTML 的完整质量检查流程，和固定单张图的外部接口测试。前者衡量 Dreamatic 总体行为，后者区分图像服务波动。独立记录正常运行、修复运行、外部接口故障运行；不要只选最好一次或只报告平均值。样本扩大后再计算服务级尾部指标，当前 15 次案例不足以承诺 SLA。
